# Проверка списка товаров

## Встроенный список URL

Обрабатывай следующие четыре страницы в указанном порядке:

```yaml
- https://www.ozon.ru/product/kofe-mehmet-efendi-naturalnyy-molotyy-250-g-1897146655/
- https://www.wildberries.ru/catalog/341662943/detail.aspx
- https://megamarket.ru/catalog/details/tureckiy-molotyy-obzharennyy-kofe-kurukahveci-mehmet-efendi-250-gr-600001530387_43321/
- https://market.yandex.ru/card/kofe-molotyy-mehmet-efendi-250-gr-zhb/102749157791
```

## Сценарий одного запуска

Перед любыми изменениями проверь наличие непустых `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в окружении. Выводи только названия и наличие, никогда значения. Если хотя бы одной переменной нет, остановись и сообщи её имя. Не создавай `.env`, не записывай учётные данные в файлы, Git, логи или сообщения.

1. Найди подключённые рабочие копии `ishchts/vibecoding-claudecode-project-388` и `ishchts/tracker-data` под `/workspace`. Проверь для каждой `git remote -v`, `git status` и `git branch --show-current`, скрывая токены и данные авторизации в выводе. Подтверди принадлежность по `origin`, а не только по имени папки. Сохраняй посторонние изменения. Если рабочей копии tracker-data нет, остановись; не клонируй её автоматически. Проверь чтение `git ls-remote origin refs/heads/main` и предварительно `git push --dry-run origin HEAD:main` из tracker-data. Успешный dry-run не заменяет итоговую проверку фактического push.
2. Прочитай существующий скилл [extract-price](../extract-price/SKILL.md). Используй его как единственный источник правил извлечения, нормализации и проверки цен и рассрочки. Не копируй эти правила в tracker. Если скиллы не зарегистрированы в интерфейсе Codex, выполняй их как инструкции из файлов.
3. В начале прогона зафиксируй дату в часовом поясе `Europe/Moscow`, например через `datetime.now(ZoneInfo("Europe/Moscow")).date().isoformat()` в Python. Прочитай [KNOWLEDGE.md](KNOWLEDGE.md) — источник правил значимости. Не округляй процент до проверки порога.
4. До извлечения новых цен получи список файлов в корне рабочей копии tracker-data, выбери предыдущий прогон по правилам ниже и прочитай его в отдельный снимок вне tracker-data. Если история повреждена, остановись до извлечения и записи.
5. Последовательно обработай каждый URL встроенного списка. Для каждого отдельно примени extract-price с одним URL в качестве входа. Получай актуальные данные; не подставляй цены из сохранённых примеров или предыдущих прогонов. Сохрани результат каждого вызова в памяти текущего прогона. При `extraction_failed` зафиксируй причину и переходи к следующему URL. Ошибку инструмента чтения страницы или браузера оформляй по контракту extract-price; не прерывай весь прогон и не пропускай строку. Если получить ни одной цены не удалось, сохраняй структурированную ошибку, а не успешный результат без цен.
6. Для каждой страницы определи магазин по домену. Название товара возьми из проверенной карточки. Если карточка недоступна и название подтвердить нельзя, укажи `—`; не придумывай название по другим страницам.
7. После обработки всех четырёх URL сформируй одну Markdown-таблицу в исходном порядке и единый JSON-массив по контракту ниже из тех же результатов. Проверь массив и сохрани свежие данные во временный файл вне tracker-data. Не возвращай четыре отдельные таблицы или отдельные JSON-ответы.
8. До записи нового JSON в историю рассчитай diff со снимком предыдущего прогона. Сохрани полный список изменений и диагностику отдельно; для итогового списка уведомлений оставь только значимые изменения согласно KNOWLEDGE.md. При первом запуске список изменений пустой.
9. Только после успешного расчёта diff сохрани массив в корне tracker-data в файле `<дата-прогона>.json`, создай отдельный коммит только с этим файлом и отправь его в origin через обычный Git. Покажи таблицу, значимые изменения, диагностику и ссылки на файл и коммит.
10. После сохранения данных отправь допустимые значимые изменения в Telegram по правилам ниже. Ошибка Telegram не должна отменять сохранение JSON, коммит или отправку в tracker-data. Не повторяй сбор цен из-за ошибки доставки.

## Выбор предыдущего прогона

Учитывай только корневые файлы с именем `YYYY-MM-DD.json`, содержащим календарно корректную дату. Отсортируй их по дате. Если есть файл за зафиксированную дату нового прогона, выбери его; иначе выбери последний файл с более ранней датой. Будущие файлы игнорируй. Если подходящего файла нет, это первый запуск: сохрани новые данные без изменений состава или цен.

Прочитай выбранный файл JSON-парсером **до извлечения и перезаписи**. Невалидный JSON, не-массив, повторные URL или нарушения контракта — ошибка истории: сообщи имя файла и причину, остановись, не выбирай незаметно более старый файл. Снимок сохраняй вне tracker-data; не перечитывай уже перезаписанный файл как предыдущий.

Используй помощник [scripts/compare_runs.py](scripts/compare_runs.py) из корня основного репозитория. Создай отдельный временный каталог для прогона. Например, для даты `2026-10-07`:

```bash
tracker_run_dir=$(mktemp -d /tmp/tracker-diff.XXXXXX)
python3 .agents/skills/tracker/scripts/compare_runs.py prepare \
  --history-dir /workspace/tracker-data \
  --run-date 2026-10-07 \
  --output "$tracker_run_dir/previous.json"
```

Подставляй фактическую дату и проверенный путь рабочей копии. Помощник сообщает выбранный исходный файл и сохраняет его проверенный массив в `previous.json`; при первом запуске снимок содержит `null`. Не редактируй снимок. Новое извлечение начни только при нулевом коде завершения этой команды.

## Расчёт diff до сохранения

Сопоставляй массивы по полному URL. Для общего URL учитывай статусы, сравнивай `regular_price`, `sale_price`, `has_credit` по KNOWLEDGE.md. Отдельно учитывай добавленные и удалённые URL. Ошибка текущего извлечения не удаляет товар и не меняет цену или рассрочку; восстановление после ошибки не создаёт новый товар и ценовой процент.

После сохранения свежего массива в `$tracker_run_dir/current.json` выполни:

```bash
python3 .agents/skills/tracker/scripts/compare_runs.py diff \
  --previous "$tracker_run_dir/previous.json" \
  --current "$tracker_run_dir/current.json" \
  --output "$tracker_run_dir/diff.json"
```

При ошибке сравнения не перезаписывай историю. Результат содержит `first_run`, `changes`, `significant_changes`, `diagnostics`. Полный `changes` нужен для проверки порога; итоговый список уведомлений — только `significant_changes`. Не добавляй диагностику к ценовым изменениям. Пустой список значимых изменений означает отсутствие значимых изменений, а не ошибку. Временный diff не записывай в корень tracker-data и не меняй формат сохранённого массива.

В итоговом пользовательском отчёте показывай только изменения с `significant: true`; не публикуй полный `changes` с незначительными изменениями. Допустимые типы: `regular_price_changed`, `sale_price_changed`, `sale_appeared`, `sale_disappeared`, `credit_appeared`, `credit_disappeared`, `product_added`, `product_removed`. Если `significant_changes` пуст, выводи точно:

```text
Значимых изменений по сравнению с предыдущим прогоном нет.
```

Таблица текущих цен и краткая диагностика могут быть показаны отдельно; ошибки не являются списком ценовых изменений. Сохраняемый JSON содержит только массив свежих результатов; полный diff и диагностика сравнения остаются вне исторического файла.

Пример одного изменения:

```json
{
  "url": "https://example.com/product",
  "change_type": "regular_price_changed",
  "field": "regular_price",
  "old_value": 1000,
  "new_value": 1100,
  "percent_change": 10,
  "significant": true,
  "reason": "Обычная цена увеличилась на 10%, порог — 1%."
}
```

## Уведомления Telegram

Для отправки используй [scripts/send.py](scripts/send.py), работающий через стандартный Python `urllib`. Из корня основного репозитория:

```bash
python3 .agents/skills/tracker/scripts/send.py "текст"
```

Формируй короткую текстовую сводку только из `significant_changes` с `significant: true`: дата Europe/Moscow, магазин/товар, тип изменения, старое и новое значения, процент при наличии. Не включай полный diff, незначимые изменения или диагностические ошибки. Изменения для URL с текущим `extraction_failed` не отправляй; они не подтверждают изменение цены, скидки или рассрочки. Ошибки отдельных URL не мешают отправке подтверждённых значимых изменений других товаров.

Если `significant_changes` пуст или после исключения ошибочных URL отправлять нечего, не вызывай send.py. В частности, не отправляй в Telegram сообщения об отсутствии изменений, CAPTCHA, `403`, `498` или восстановлении данных. Тест доставки выполняй только при явном запросе пользователя, а не при каждом прогоне.

Сводка должна укладываться в 4096 UTF-16 единиц. Если список длиннее, сократи формулировки и сообщи число остальных значимых изменений; не включай учётные данные. Для динамического текста запускай скрипт через `subprocess.run(["python3", путь_send_py, текст], check=False)` без `shell=True` и без подстановок в shell. Отправляй обычный текст без HTML/Markdown-разметки Telegram.

Скрипт вызывает только `sendMessage` на `api.telegram.org`, сохраняет проверку TLS, не следует перенаправлениям. Учётные данные берутся только из окружения; поддерживаются привязки прокси среды. Успешный ответ `ok: true` даёт вывод `Отправлено.` и код 0; ошибка даёт безопасное описание и ненулевой код без токена, полного адреса запроса или тела ответа.

Запиши результат доставки отдельно от ценового массива. Если доставка не удалась, сообщи безопасную причину пользователю, сохрани JSON и продолжи завершение прогона. Не откатывай файлы, не добавляй ошибку Telegram в массив цен, не считай её ошибкой извлечения товара. Не повторяй отправку автоматически: после сетевой ошибки доставка может быть неопределённой, а повтор создаст дубликат.

## Формат таблицы

Используй ровно эти столбцы:

```text
Товар | Магазин | URL | regular_price | sale_price | has_credit | status | reason
```

- Для результата с данными товара перенеси цены и булево значение `has_credit` из extract-price без переинтерпретации. Укажи статус `success`. Значения `null` у цен показывай как `null`; отсутствие скидки не является ошибкой. Если extract-price отдельно сообщил причину частичного результата, перенеси её в `reason`, иначе укажи `—`.
- При `extraction_failed` укажи `—` во всех трёх столбцах `regular_price`, `sale_price`, `has_credit`; статус — `extraction_failed`, `reason` — краткая фактическая причина из ответа extract-price. Не подставляй `false` вместо неизвестного наличия рассрочки.
- В столбце URL сохраняй полный исходный URL. Допустима Markdown-ссылка с названием магазина в качестве подписи и полным URL в адресе ссылки.
- Экранируй символы `|` в названии и причине, а переносы строк заменяй пробелами, чтобы не нарушить структуру таблицы.
- Таблица должна содержать ровно одну строку для каждого из четырёх URL, включая недоступные страницы. Ошибка отдельного магазина не является ошибкой всего прогона.

## JSON и сохранение через Git

В файле должен быть верхнеуровневый JSON-массив, содержащий ровно один объект для каждого URL в исходном порядке. Не добавляй обёртку `run_date`/`items`, Markdown или свободный текст. Используй UTF-8, отступ в два пробела и завершающий перевод строки.

Успешный элемент — исходный URL и поля результата extract-price:

```json
{
  "url": "https://example.com/product",
  "regular_price": 1900,
  "sale_price": 933,
  "has_credit": false
}
```

Цены сохраняй числами либо `null`, если значение не найдено согласно extract-price; `has_credit` — проверенным булевым значением. При ошибке добавь URL к структурированной ошибке extract-price и не включай цены или неизвестный `has_credit`:

```json
{
  "url": "https://example.com/product",
  "status": "extraction_failed",
  "reason": "Карточка товара недоступна: сайт показывает CAPTCHA."
}
```

Ошибки отдельных сайтов не препятствуют сохранению массива. Дату бери из зафиксированного начала прогона в Europe/Moscow; имя файла — `YYYY-MM-DD.json`. Для прогона 7 октября 2026 года это `2026-10-07.json`. При новом запуске вычисляй актуальную дату, не используй этот пример как константу.

Перед записью проверь существующий файл за эту дату и сохрани чужие незакоммиченные изменения. Новый прогон за тот же день обновляет этот файл; предыдущая закоммиченная версия остаётся в истории Git. Не изменяй README или другие файлы. Работай только обычным Git из рабочей копии tracker-data; GitHub MCP и GitHub API не используй.

1. Сохрани валидированный массив в целевой файл. Повторно прочитай его JSON-парсером, проверь четыре URL, порядок, отсутствие дубликатов, типы цен и корректность контрактов успеха и ошибки.
2. Выполни `git add -- <дата-прогона>.json`. Проверь, что staged diff включает только этот файл; не включай посторонние staged-изменения в коммит. Сообщение при создании: `Add price tracker run for YYYY-MM-DD`, при обновлении: `Update price tracker run for YYYY-MM-DD`. Если содержимое совпадает с уже сохранённым, не создавай пустой коммит.
3. Выполни `git push origin HEAD:main`. Не используй force push. При отказе остановись и сообщи репозиторий, команду, точный текст ошибки и этап остановки; не объявляй сохранение на GitHub успешным.
4. Проверь удалённую ветку через `git ls-remote origin refs/heads/main` и при необходимости `git fetch origin main`. Сопоставь файл в полученной удалённой версии с текущим JSON-прогоном. Приведи ссылку `https://github.com/ishchts/tracker-data/blob/main/YYYY-MM-DD.json` и ссылку на коммит.

Если tracker-data отсутствует, нет права записи или push запрещён, остановись с указанием репозитория, команды, точной ошибки и этапа. Не обходи отказ другим способом доступа. Код скилла остаётся в основном репозитории, JSON-прогоны — только в tracker-data.

## Проверка перед ответом

Убедись, что предыдущий файл выбран до извлечения, проверен и прочитан до перезаписи; будущие файлы не использованы. Проверь diff до сохранения, порог 1% без предварительного округления, отсутствие ценовых изменений из ошибок и фильтрацию значимых изменений по KNOWLEDGE.md. Все четыре URL должны быть обработаны последовательно; таблица и JSON соответствуют одним результатам. Проверь дату Europe/Moscow, JSON-массив, отдельный коммит в tracker-data, успешный push и совпадение удалённого файла с текущим прогоном. Проверка доступа ко всем маркетплейсам не является условием сохранения. Проверь фильтрацию уведомлений, безопасный результат доставки и отсутствие потери JSON при ошибке Telegram. При отсутствии допустимых значимых изменений уведомление не отправляется.
