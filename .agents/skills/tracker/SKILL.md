# Проверка списка товаров

## Встроенный список URL

Обрабатывай следующие четыре страницы в указанном порядке:

```yaml
- https://www.ozon.ru/product/kofe-mehmet-efendi-naturalnyy-molotyy-250-g-1897146655/
- https://www.wildberries.ru/catalog/341662943/detail.aspx
- https://megamarket.ru/catalog/details/tureckiy-molotyy-obzharennyy-kofe-kurukahveci-mehmet-efendi-250-gr-600001530387_43321/
- https://market.yandex.ru/card/kofe-molotyy-mehmet-efendi-250-gr-zhb/102749157791
```

## Сценарий одного запуска

1. Найди подключённые рабочие копии `ishchts/vibecoding-claudecode-project-388` и `ishchts/tracker-data` под `/workspace`. Проверь для каждой `git remote -v`, `git status` и `git branch --show-current`, скрывая токены и данные авторизации в выводе. Подтверди принадлежность по `origin`, а не только по имени папки. Сохраняй посторонние изменения. Если рабочей копии tracker-data нет, остановись; не клонируй её автоматически. Проверь чтение `git ls-remote origin refs/heads/main` и предварительно `git push --dry-run origin HEAD:main` из tracker-data. Успешный dry-run не заменяет итоговую проверку фактического push.
2. Прочитай существующий скилл [extract-price](../extract-price/SKILL.md). Используй его как единственный источник правил извлечения, нормализации и проверки цен и рассрочки. Не копируй эти правила в tracker. Если скиллы не зарегистрированы в интерфейсе Codex, выполняй их как инструкции из файлов.
3. В начале прогона зафиксируй дату в часовом поясе `Europe/Moscow`, например через `datetime.now(ZoneInfo("Europe/Moscow")).date().isoformat()` в Python. Последовательно обработай каждый URL встроенного списка. Для каждого отдельно примени extract-price с одним URL в качестве входа. Получай актуальные данные; не подставляй цены из сохранённых примеров или предыдущих прогонов.
4. Сохрани результат каждого вызова в памяти текущего прогона. При `extraction_failed` зафиксируй причину и переходи к следующему URL. Если инструмент чтения страницы или браузер выдаёт ошибку, применяй контракт ошибки extract-price; не прерывай весь прогон и не пропускай строку. Если получить ни одной цены не удалось, сохраняй структурированную ошибку `extraction_failed` с фактической причиной, а не успешный результат без цен.
5. Для каждой страницы определи магазин по домену. Название товара возьми из проверенной карточки. Если карточка недоступна и название подтвердить нельзя, укажи `—`; не придумывай название по другим страницам.
6. После обработки всех четырёх URL сформируй одну Markdown-таблицу в исходном порядке и единый JSON-массив по контракту ниже из тех же результатов. Не возвращай четыре отдельные таблицы или отдельные JSON-ответы.
7. Проверь массив, сохрани его в корне рабочей копии tracker-data в файле `<дата-прогона>.json`, создай отдельный коммит только с этим файлом и отправь его в origin через обычный Git. После успешного push покажи таблицу и ссылки на файл и коммит.

## Формат таблицы

Используй ровно эти столбцы:

```text
Товар | Магазин | URL | regular_price | sale_price | has_credit | status | reason
```

- Для результата с данными товара перенеси цены и булево значение `has_credit` из extract-price без переинтерпретации. Укажи статус `success`. Значения `null` у цен показывай как `null`; отсутствие скидки не является ошибкой. Если extract-price отдельно сообщил причину частичного результата, перенеси её в `reason`, иначе укажи `—`.
- При `extraction_failed` укажи `—` во всех трёх столбцах `regular_price`, `sale_price`, `has_credit`; статус — `extraction_failed`, `reason` — краткая фактическая причина из ответа extract-price. Не подставляй `false` вместо неизвестного наличия рассрочки.
- В столбце URL сохраняй полный исходный URL. Допустима Markdown-ссылка с названием магазина в качестве подписи и полным URL в адресе ссылки.
- Экранируй символы `|` в названии и причине, а переносы строк заменяй пробелами, чтобы не нарушить структуру таблицы.
- Таблица должна содержать ровно одну строку для каждого из четырёх URL, включая недоступные страницы. Ошибка отдельного магазина не является ошибкой всего прогона.

## JSON и сохранение через Git

В файле должен быть верхнеуровневый JSON-массив, содержащий ровно один объект для каждого URL в исходном порядке. Не добавляй обёртку `run_date`/`items`, Markdown или свободный текст. Используй UTF-8, отступ в два пробела и завершающий перевод строки.

Успешный элемент — исходный URL и поля результата extract-price:

```json
{
  "url": "https://example.com/product",
  "regular_price": 1900,
  "sale_price": 933,
  "has_credit": false
}
```

Цены сохраняй числами либо `null`, если значение не найдено согласно extract-price; `has_credit` — проверенным булевым значением. При ошибке добавь URL к структурированной ошибке extract-price и не включай цены или неизвестный `has_credit`:

```json
{
  "url": "https://example.com/product",
  "status": "extraction_failed",
  "reason": "Карточка товара недоступна: сайт показывает CAPTCHA."
}
```

Ошибки отдельных сайтов не препятствуют сохранению массива. Дату бери из зафиксированного начала прогона в Europe/Moscow; имя файла — `YYYY-MM-DD.json`. Для прогона 7 октября 2026 года это `2026-10-07.json`. При новом запуске вычисляй актуальную дату, не используй этот пример как константу.

Перед записью проверь существующий файл за эту дату и сохрани чужие незакоммиченные изменения. Новый прогон за тот же день обновляет этот файл; предыдущая закоммиченная версия остаётся в истории Git. Не изменяй README или другие файлы. Работай только обычным Git из рабочей копии tracker-data; GitHub MCP и GitHub API не используй.

1. Сохрани валидированный массив в целевой файл. Повторно прочитай его JSON-парсером, проверь четыре URL, порядок, отсутствие дубликатов, типы цен и корректность контрактов успеха и ошибки.
2. Выполни `git add -- <дата-прогона>.json`. Проверь, что staged diff включает только этот файл; не включай посторонние staged-изменения в коммит. Сообщение при создании: `Add price tracker run for YYYY-MM-DD`, при обновлении: `Update price tracker run for YYYY-MM-DD`. Если содержимое совпадает с уже сохранённым, не создавай пустой коммит.
3. Выполни `git push origin HEAD:main`. Не используй force push. При отказе остановись и сообщи репозиторий, команду, точный текст ошибки и этап остановки; не объявляй сохранение на GitHub успешным.
4. Проверь удалённую ветку через `git ls-remote origin refs/heads/main` и при необходимости `git fetch origin main`. Сопоставь файл в полученной удалённой версии с текущим JSON-прогоном. Приведи ссылку `https://github.com/ishchts/tracker-data/blob/main/YYYY-MM-DD.json` и ссылку на коммит.

Если tracker-data отсутствует, нет права записи или push запрещён, остановись с указанием репозитория, команды, точной ошибки и этапа. Не обходи отказ другим способом доступа. Код скилла остаётся в основном репозитории, JSON-прогоны — только в tracker-data. Сравнение прогонов и уведомления Telegram пока не выполняй.

## Проверка перед ответом

Убедись, что все четыре URL обработаны последовательно, порядок и восемь столбцов сохранены, таблица и JSON соответствуют одним результатам, причины ошибок присутствуют. Проверь дату Europe/Moscow, JSON-массив из четырёх элементов, отдельный коммит в tracker-data, успешный push и совпадение удалённого файла с текущим прогоном. Проверка доступа ко всем маркетплейсам не является условием сохранения.
